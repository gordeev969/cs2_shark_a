# Общая очередь и приоритет статистики

Очередь общая для всех Steam-аккаунтов на сервере. API сразу сохраняет загруженную демку и возвращает HTTP 202. Пользователь может загрузить следующую запись, открыть готовые отчёты или уйти со страницы: задания живут в SQLite, а не в браузере.

## Порядок работы

1. Готовая статистика читается непосредственно из SQLite без ожидания парсера.
2. Сохранённые демки разбираются по одной, FIFO по номеру задания. Повторная попытка неудачного импорта становится в конец очереди.
3. Когда подготовленных демок нет, воркер берёт запрос синхронизации Steam. После скачивания одной записи сначала разбираются доступные демки, затем скачивается следующая. Активная загрузка или разбор не прерываются новым заданием.

Статусы: `queued` → `processing` → `ready` / `failed`. В импорте, списке матчей и ожидающем отчёте отображается `queue_position`: позиция среди ожидающих разборов всей очереди, без активного задания. Чужие матчи не раскрываются; дашборд показывает число заданий текущего аккаунта. Позиция не является прогнозом времени: размеры и сложность демок различаются.

Неизвестные аккаунты и готовые показатели не подменяются тестовыми данными. Результат сохраняется транзакционно; ошибка одной демки не останавливает следующую.

## Единственный воркер и восстановление

Таблица `work_queue` сохраняет задания импорта и синхронизации. Блокировка файла `.work-queue.lock` выбирает единственный воркер среди процессов API, использующих одну папку `CS2_DATA_DIR`. На Linux дочерний native-парсер наследует блокировку: аварийное завершение родителя не позволяет запустить второй парсер одновременно с ещё работающим первым.

После получения блокировки новый воркер возвращает незавершённые задания в очередь. Отсутствующий исходный файл даёт `failed` с предложением загрузить его повторно. Обычная остановка завершает активный разбор и оставляет ожидающие задания для следующего запуска. Перезапуск во время синхронизации может продолжаться дольше, поскольку Steam-задача завершает текущую работу.

Миграция SQLite с версии 2 на 3 добавляет очередь, сохраняет готовую статистику и восстанавливает прежние ожидающие импорты по времени загрузки. Перед обновлением сохраняйте резервную копию папки данных; старый backend не понимает схему версии 3.

Это решение для одного сервера и локального диска. Независимые базы на разных VPS образуют независимые очереди. Redis не нужен. Большое количество API-процессов расходует дополнительную память без ускорения парсера, поэтому на маленьком VPS достаточно одного процесса API.

## Лимиты и маленький VPS

`CS2_MAX_PENDING_IMPORTS=8` ограничивает суммарное число ожидающих и активных демок всех пользователей. Проверка и резервирование слота атомарны. При заполнении новый импорт получает HTTP 429 и понятную ошибку; повтор уже принятой или готовой демки не занимает слот. Синхронизация при заполнении сообщает ошибку; её можно повторить после освобождения места. Этот лимит не ограничивает количество HTTP-соединений или временно передаваемых файлов, поэтому публичный сервер дополнительно нуждается в ограничении одновременных загрузок на прокси.

`CS2_MAX_UPLOAD_MB=512` ограничивает один файл. При восьми заданиях исходники могут занять до 4 GiB, помимо ОС, образов, SQLite, скачиваемой сжатой записи и временных файлов. Для диска 10 GB разумно начать с `CS2_MAX_PENDING_IMPORTS=2` и оставить `CS2_RETAIN_DEMOS=false`. Это предотвращает накопление обработанных исходников; статистика сохраняется. Незарезервированные `incoming-*.tmp` после аварии удаляйте только при остановленном backend, чтобы не затронуть активную передачу другого процесса.

Парсер использует по одному потоку Polars и Rayon. Очередь ограничивает одновременную тяжёлую работу, но не уменьшает память, необходимую для одной демки. Для 1 CPU / 768 MB RAM нужно измерить пик RSS на полноценной Premier-записи вместе с API, ОС и Steam GC-сервисом. Swap может пережить краткий пик, но не заменяет эту проверку; гарантии стабильной работы на 768 MB нет.

GitHub Pages показывает сохранённую статистику. Выполнение очереди, Steam-вход и импорт доступны в серверной версии, поскольку Pages не запускает Python и SQLite.
