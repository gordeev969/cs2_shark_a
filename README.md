# CS2 Premier Analyzer

Бесплатный режим просмотра: [GitHub Pages](docs/GITHUB_PAGES.md). Полная версия со Steam и своим парсером: [Render](docs/RENDER.md).

Локальный CS2 Premier Analyzer: вход через Steam, подключение истории CS2, личный дашборд, последние матчи с K/D/A и ADR, отчёты матчей и профили игроков. Реальные `.dem` разбираются через `demoparser2`; статистика, история и аналитика сохраняются в SQLite. Русский frontend построен по FSD, числовые показатели не подставляются из макетов.

Расчёт демки работает автономно без AI. Для Steam-входа нужна сеть; автоматическая история дополнительно требует server Steam Web API key и Steam Game Coordinator worker. Полная инструкция: [docs/STEAM.md](docs/STEAM.md).

Исходные требования MVP (Steam-этап добавлен по последнему запросу пользователя): [MVP_SPEC.md](MVP_SPEC.md), [CODEX_TASK.md](CODEX_TASK.md). Архитектура frontend: [docs/FRONTEND_ARCHITECTURE.md](docs/FRONTEND_ARCHITECTURE.md). Результаты проверки текущей реализации: [docs/VALIDATION.md](docs/VALIDATION.md).

## Запуск без Docker

Нужны Python 3.11+ и Node.js 22.12+; рекомендуются Python 3.12 и Node.js 22. Следующие команды выполняются из корня проекта. Установка зависимостей и Steam-вход требуют сети; расчёт загруженной демки выполняется локально.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
npm --prefix frontend ci
npm --prefix gc-worker ci
cp .env.example .env
```

В первом терминале запустите API:

```bash
set -a
. ./.env
set +a
export STEAM_PUBLIC_URL=http://127.0.0.1:5173
.venv/bin/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале:

```bash
npm --prefix frontend run dev
```

Откройте **http://127.0.0.1:5173**. Vite передаёт `/api` локальному backend на порту 8000. API health: http://127.0.0.1:8000/api/health; OpenAPI: http://127.0.0.1:8000/docs. Оба процесса привязаны к localhost. Backend проверяет Host и браузерный Origin; пользовательские порты потребуют согласованного изменения этой конфигурации.

`make install`, `make dev-backend` и `make dev-frontend` дают те же операции. `make dev-backend` использует значения по умолчанию или уже экспортированные переменные; `.env` при native-запуске автоматически не загружается. Для Windows активируйте `.venv\Scripts\activate`, экспортируйте переменные своим shell и используйте `python` вместо `.venv/bin/python`.

## Docker Compose

```bash
cp .env.example .env
docker compose up --build -d
```

Откройте **http://127.0.0.1:8000**. Nginx обслуживает собранный frontend и проксирует `/api`; вложенные маршруты React открываются напрямую. Единственный host-port привязан к `127.0.0.1`. Backend не публикует порт на host; исходящая сеть доступна для Steam и загрузки демо. Его `0.0.0.0` относится к сетевому пространству контейнера. Данные хранятся в именованном volume `analyzer-data`.

```bash
docker compose logs -f backend
docker compose down
```

`down` сохраняет volume. Не используйте `down -v`, если хотите сохранить импортированную историю. Native SQLite и Docker volume — независимые хранилища. Конфигурация контейнеров включена в поставку; успешность Docker build/runtime следует проверять отдельно по [docs/VALIDATION.md](docs/VALIDATION.md).

Сборка использует BuildKit. Для окружения с HTTPS-прокси Dockerfiles поддерживают необязательный build secret `proxy_ca`: npm расширяет доверенные сертификаты через `NODE_EXTRA_CA_CERTS`, pip использует переданный объединённый CA bundle через `PIP_CERT`. Сертификат передаётся отдельным локальным Compose override с `build.secrets` и не сохраняется в image layers. Без такого override используется обычное системное доверие; проверка TLS всегда включена.

## Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `CS2_DATA_DIR` | `./data` | Папка SQLite и временных загрузок; в Compose всегда `/data` |
| `CS2_MAX_UPLOAD_MB` | `512` | Лимит одного файла, в MiB |
| `CS2_PARSER_TIMEOUT` | `180` | Максимальная длительность subprocess парсера, секунды |
| `CS2_RETAIN_DEMOS` | `false` | Сохранять исходные демки после завершения задания |
| `CS2_REQUIRE_STEAM_LOGIN` | `true` | Требовать вход Steam; `false` включает автономный режим локальных импортов |
| `STEAM_PUBLIC_URL` | `http://127.0.0.1:8000` | Адрес в браузере для callback; у native Vite — порт 5173 |
| `STEAM_WEB_API_KEY` | пусто | Server key для публичного Steam-профиля и discovery новых матчей |
| `CS2_SECRET_KEY` | локальный файл | Fernet key для Game Authentication Code; сохранить вместе с SQLite |
| `CS2_GC_URL` | пусто | Внутренний адрес GC worker, например `http://gc-worker:8001` в Compose |
| `CS2_GC_SECRET` | пусто | Общий случайный секрет backend/worker, от 24 символов |

При увеличении лимита в Compose измените также `client_max_body_size` в `frontend/nginx.conf`, учитывая служебные байты multipart. Изменение retention влияет на последующие задания; ранее удалённые демки не восстанавливаются. При входе SteamID64 определяется подтверждённым аккаунтом. В автономном режиме его можно указать в настройках. Компактный вид сохраняется в SQLite. SteamID не обязан присутствовать в импортированных матчах: личная статистика появится после его первого успешного импорта.

AI-интеграция в этом MVP не реализована: `ai_enabled=false`, исходящих AI-запросов нет. Числовая статистика и заметки всегда доступны локально.

## Импорт настоящей демки

1. Получите запись собственной игры в CS2 либо используйте демку, которую вам разрешено анализировать. При стандартном запуске сначала войдите Steam. Для автономной работы без Steam задайте `CS2_REQUIRE_STEAM_LOGIN=false`.
2. Если загрузка имеет формат `.dem.bz2` или находится в `.zip`, распакуйте её самостоятельно. Загрузчик принимает только отдельный несжатый `.dem` с бинарной сигнатурой CS2 `PBDEMS2`; CS:GO-демки не поддерживаются.
3. Откройте «Импорт», выберите файл и дождитесь `ready`. Один файл обрабатывается за раз. В случае `failed` страница показывает причину ошибки; повторная загрузка запускает неудачный импорт заново.
4. Откройте отчёт матча и любого участника. Свой SteamID определяется входом; в автономном режиме выберите его в настройках. Профиль отражает локально доступную выборку матчей.

SHA-256 содержимого определяет идентичность файла: повторный успешный импорт возвращает существующий матч. Имя файла не используется как путь хранения. Загрузка ограничена по размеру, временные файлы находятся в отдельной папке, native-парсер запускается в subprocess с timeout. SQLite хранит матчи, стабильные SteamID64 игроков, статистику и детали завершённых раундов. Возобновление очереди после перезапуска работает, пока исходный файл сохранён.

## Метрики и точность

Адаптер использует закреплённый `demoparser2==0.42.0` и реальные события `player_death`, `player_hurt`, `round_freeze_end`/`round_start`, `round_end`, `round_officially_ended`, `player_spawn`. Границы раундов сверяются с `total_rounds_played`, разминка исключается. После `round_end` бой может продолжаться: убийства и урон до `round_officially_ended` входят в статистику предыдущего раунда; начало следующего раунда и его buytime туда не входят. При отсутствии официального конца используется подтверждённый следующий `round_start`, затем сам `round_end`; источник границы сохранён в данных раунда. События после завершения матча исключаются. Участие подтверждается snapshot на начале раунда либо событиями появления/боя. Учитываются **только завершённые раунды**, для которых удалось подтвердить границы. Игроки с надёжным SteamID64 отображаются даже при недоступной статистике.

| Показатель | Формула и политика |
| --- | --- |
| K | Убийства противников; самоубийства и тимкиллы исключены |
| D | Все смерти игрока, включая самоубийства и смерть от союзника |
| A | Ассист из события игры при подтверждённых командах; неизвестные обязательные поля дают `null` |
| K/D | `K / max(D, 1)`; рядом всегда доступны K и D |
| HS% | `headshot enemy kills / K × 100`; при K=0 показывается 0% |
| K/R | `K / rounds_played` |
| ADR | `effective enemy health damage / rounds_played`; неполные доказательства дают `null` |

ADR считается по **наблюдаемому изменению целочисленного HP жертвы**, а не по урону оружия. Вражеский урон гранат и огня входит в показатель. Урон союзникам и себе исключается, overkill ограничен фактической потерей HP. Для ненулевого остатка HP разница `dmg_health` и изменения HP до 1 допускается из-за наблюдаемого округления событий движка. Большее расхождение, неизвестное начальное/остаточное HP или команды исключают достоверный ADR: он становится `null` для участников затронутого раунда и итогового матча, а причина сохраняется. Поэтому значение может немного отличаться от стороннего сервиса с другой политикой округления.

Команды A/B определяются по сторонам первого подтверждённого участия и сохраняют принадлежность через смену сторон. Это локальные обозначения, не официальные названия команд. Итоговый счёт берётся из подтверждённого `cs_win_panel_match` и согласованных `team_rounds_total`. При отсутствии этих данных отображается «нет данных»; счёт не угадывается из числа сохранённых раундов. Дата игры не подменяется датой импорта; при получении подтверждённого `matchtime` из GC она сохраняется отдельно.

В доступной контрольной записи Mirage есть 10 участников, 9 завершённых игровых раундов и итоговый счёт 8:2 при surrender. Итоговый счёт может включать присуждённый после сдачи раунд, у которого нет полного набора боевых событий. Поэтому число сыгранных раундов и сумма финального счёта могут отличаться. Сводка фактической проверки этой записи находится в `docs/VALIDATION.md`.

Профиль агрегирует K/D как отношение суммарных K и D, HS% как отношение суммарных headshot kills и K, K/R по общему числу раундов. ADR взвешен количеством раундов и включает только матчи с достоверным effective_damage; `adr_matches` и `adr_rounds` явно показывают охват. Если для K/D/HS% отсутствует обязательное значение хотя бы в одном матче, общий показатель неизвестен. Личная скользящая сводка использует до 20 последних импортов; графики и окна упорядочены **по дате игры при её наличии, иначе по времени импорта**; время в интерфейсе обозначает фактический источник.

## Аналитика и ограничения

Заметки матча объясняют посчитанные метрики. Правила K/R≥0,8 и K/R<0,5 — прозрачные пороги приложения для разбора собственных раундов, не мировая эталонная выборка. При менее 10 локальных матчах аналитика сообщает о недостатке данных. Начиная с 10 сравниваются последние 5 импортов и предыдущие до 10: выводятся обе выборки, значения ADR/K/D и разница. Это описание собственной истории без античит-вердиктов или оценки вероятности читерства.

Premier Rating, KAST, entry, trades, clutch и неизвестные события не рассчитываются. Данные могут быть неполными у обрезанной записи, при переподключении, смене состава или неподдерживаемой версии replay. Причины отсутствующих значений и поля событий доступны в диагностике отчёта. Проверка одной Mirage-записи не подтверждает все режимы Premier, карты, overtime и версии формата: для этих случаев нужны дополнительные настоящие демки с известной итоговой таблицей.

## Проверки

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check backend
.venv/bin/python -m ruff format --check backend
npm --prefix frontend run lint
npm --prefix frontend run format:check
npm --prefix frontend test
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

Либо `make check`. Unit/API-тесты дополнительно покрывают Steam OpenID/CSRF/session/logout, account scoping, discovery, GC HTTP, ограниченную BZip2-загрузку и шифрование кода. `npm --prefix gc-worker test` проверяет uint64 correlation, очередь и таймауты клиентского GC-протокола. Unit/API-тесты покрывают формулы, границы раундов, команды, дружеский урон и overkill, отсутствующие поля, загрузку и дедупликацию, SQLite-агрегацию, порог истории, ошибки native-парсера и timeout. Frontend-тесты покрывают форматирование и FSD-границы. Синтетические fixtures используются только в тестах.

Опциональный интеграционный тест настоящей демки:

```bash
CS2_TEST_DEMO=/absolute/path/to/legally-obtained.dem .venv/bin/python -m pytest -q backend/tests/test_parser.py
```

Без `CS2_TEST_DEMO` этот тест пропускается с явной причиной. Для полной приёмки на вашей версии Premier загрузите настоящий `.dem`, сравните K/D/A/HS и счёт с игровым табло, проверьте смену сторон/overtime и повторный импорт. Проверка структуры одного replay и арифметики fixtures не заменяет такое сравнение.

Браузерные E2E-проверки используют контролируемые ответы для Steam/connect/logout, а импорт настоящей демки идёт через реальный backend. Они проверяют русский интерфейс, мобильную навигацию, ошибочный файл, а с настоящей демкой — импорт, участников, профиль, настройки и дедупликацию. Перед запуском остановите серверы на 8000/5173 и Compose: Playwright создаёт отдельную временную базу при запуске собственного backend, но переиспользует уже работающие серверы.

```bash
npm --prefix frontend exec playwright install chromium
CS2_TEST_DEMO=/absolute/path/to/legally-obtained.dem npm --prefix frontend run test:e2e
```

Без демки пропускается только сценарий успешного реального импорта. Установка Chromium требует сети. `make test-e2e` запускает тот же набор; `make check` включает unit/API, форматирование, линтеры, typecheck и build.

Smoke check запущенного API:

```bash
curl http://127.0.0.1:8000/api/health
# Следующие команды доступны без сессии только при CS2_REQUIRE_STEAM_LOGIN=false
curl -F file=@/absolute/path/to/match.dem http://127.0.0.1:8000/api/matches/import
curl http://127.0.0.1:8000/api/matches
```

## Диагностика и данные

При ошибке загрузки проверьте расширение, распаковку, размер и сигнатуру CS2. При timeout увеличьте `CS2_PARSER_TIMEOUT` и перезапустите backend; повреждённый replay увеличение timeout не исправит. При неизвестных метриках откройте диагностические сообщения матча. После исправления конфигурации можно повторить неудачный импорт того же файла.

Native-файлы находятся в `CS2_DATA_DIR/analyzer.sqlite3` и `CS2_DATA_DIR/uploads`. По умолчанию демка удаляется после успешного или неудачного завершения разбора; нормализованная статистика остаётся. Для резервной копии остановите backend и скопируйте всю папку данных. Статистика, настройки и очередь остаются локально. Для входа и синхронизации приложение обращается к Steam/Valve. Публичная история посторонних игроков, телеметрия и AI не используются. Сохраняйте также `.cs2-secret-key`; SteamClient-сессию `.secrets` держите отдельно от исходников.

## Steam → CS2 → дашборд

После входа откроется подключение CS2. Введите Game Authentication Code и sharing code одного недавнего матча. При настроенном сервере синхронизация откроет личный дашборд и заполнит его после разбора доступных демок. Если конфигурация неполная или запись удалена Valve, интерфейс показывает причину. Полная история всех прошлых матчей и Premier Rating не обещаются.

Для автозагрузки настройте `STEAM_WEB_API_KEY`, войдите в GC worker через QR и задайте общий `CS2_GC_SECRET`: [gc-worker/README.md](gc-worker/README.md). Live Steam/GC без вашего аккаунта не проверялся; секреты вводятся локально, не в чате.

Скриншоты работающего интерфейса: [дашборд](docs/screenshots/dashboard-desktop.png), [мобильный дашборд](docs/screenshots/dashboard-mobile.png), [вход Steam](docs/screenshots/steam-login.png). Статистика дашборда вычислена из настоящего replay в автономном режиме.

## Публикация в интернете

Простой вариант без VPS: [Render](docs/RENDER.md), готовые `render.yaml` и single-service Dockerfile. Он запускает frontend, backend и реальный парсер с сохраняемой SQLite; автозагрузка демок требует отдельного GC worker.

На собственном сервере: [Docker + HTTPS](docs/DEPLOYMENT.md), `compose.production.yaml` и `bash deploy/start.sh`. Публичное развёртывание — явный opt-in; обычный Compose остаётся localhost-only.
